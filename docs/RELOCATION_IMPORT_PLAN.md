# 지장이설 — 좌표 기반 시설·케이블·경로 임포트 설계 (v0.1)

> 작성 2026-06-13. 목적: LGU+ 시스템에서 추출한 좌표를 CSV로 업로드해 시설·케이블·도로 경로를
> 지도·도식에 정확히 그린다. **이미지를 외부로 보내지 않는 로컬/구조화 입력 방식**. 코드 들어가기
> 전에 입력 방식·파일 포맷·프로젝트 구분·기존 확장·리스크를 모두 점검해 시행착오를 최소화한다.

---

## 0. 배경 (owner 확인 사항 종합)

- 좌표는 **LGU+ 시스템에서 시설별·경로 꺾임점별로 추출 가능** (`mx`=경도, `my`=위도, WGS84 추정).
- 케이블은 **단순 A↔B 연결이 아니라 도로·골목을 따라가고 분기**한다 → 경로(꺾임점) 데이터 필요.
- 같은 도로에 **보통 4~8조, 많으면 20조**가 평행하게 지나간다. owner는 **확대해서 평행선으로** 본다
  (LGU+ 화면도 평행 오프셋 + 색=규격 + 점선=설치구분으로 표시).
- 이미지 외부 전송(클로드 API 등)은 **LGU+ 계약 확인 전까지 보류** → 로컬/구조화 입력이 정공법.

### 이번 작업의 우선순위 (owner 2026-06-13)

- **주 작업 = 기존 시설물 이설(이동)**. 기시설을 시스템에 올리고 옮기는 게 먼저.
- **절체용 도식 상세 설계는 보류** — 시설을 옮긴 뒤 실제 작업환경에서 도식을 구체적으로 검토해 확정.
  (도식은 지리를 안 따르는 절체용 연결도라는 원칙만 §2-3 에 고정. 세부 형태는 그때.)
- **실행 전 계획 우선** — OpenCV 등 모든 입력 가능성을 §1.5 에 충분히 비교한 뒤 실행 결정.

## 1.5 입력 방식 — 전체 가능성 검토 (OpenCV 포함)

owner 요청으로 "좌표 CSV" 외 모든 입력 가능성을 비교한다. 결론부터: **시설(점)과 경로(선)는 최적
방식이 다르다.** 특히 같은 도로에 4~20조가 평행하므로, 이미지에서 선을 분리 추출하는 건 매우 어렵다.

### 방식 비교 (시설 / 케이블·경로 따로)

| 방식 | 시설(점) | 경로(선·다조) | 유출 | 수고 | 난이도 |
|---|---|---|---|---|---|
| **A. 좌표 CSV 임포트** | ◎ 정확 | ◎ 꺾임점 좌표열로 정확 | 없음 | 좌표 추출(시설·꺾임점) | 낮음 |
| **B. 로컬 OpenCV 이미지** | ○ 색 기반 검출(작동 PoC 있음) | △ **4~20 평행선 분리 매우 어려움** | 없음(브라우저) | 캡처 1장 | 시설 중·경로 높음 |
| **C. 하이브리드** (OpenCV 픽셀검출 + 기준점 2~3개 지오레퍼런싱) | ○ 위치 정밀 | △ 경로는 여전히 어려움 | 없음 | 캡처 + 기준점 2~3 | 높음 |
| **D. AI 비전** (Claude 등) | ◎ 종류·연결 해석 | ○ 추정(검토 필요) | **국외 전송** | 캡처 1장 | 낮음(보류 — 계약) |

### OpenCV(로컬) 가능성 — 정직한 평가

브라우저 안에서 픽셀을 분석하므로 **유출 0**. 구성요소별:

- **시설 점 검출** — 색·모양 덩어리(blob) 검출. **이미 기본 PoC 구현됨**
  ([ScreenCaptureImport.tsx](../src/app/relocation/[id]/ScreenCaptureImport.tsx)). 보정 클릭 →
  같은 색 시설 자동 검출 → 시설 생성. 실데이터 튜닝 필요하나 **현실적**.
- **선(경로) 벡터화** — 화면의 케이블 선을 추적해 꺾임점 polyline 으로. **여기가 진짜 난관**:
  같은 도로에 **4~20조가 색·점선만 다른 채 평행**(owner 확인) → 교차·겹침에서 어느 선이 누구 건지
  자동 분리가 매우 불안정. 색별 마스킹으로 어느 정도 나눠도 20조 분리는 비현실적.
- **OCR(시설ID·전주명)** — Tesseract.js 등. 한글 + 작은 글자라 정확도 들쭉날쭉. 보조 수단.
- **지오레퍼런싱** — 픽셀 좌표를 실제 GPS로: 기준점 2~3개 좌표만 알면 전체 환산(affine). OpenCV로
  점을 정밀 검출했을 때 위치를 GPS화하는 용도.

### 추출 자동화 — 타이핑 없이 (owner 2026-06-13: "캡처만 가능, 타이핑은 무리")

전주 조회 패널/SMS 는 **깔끔한 구조화 텍스트**(라벨:값 + 좌표 URL)라, 지도(20조 평행선)와 **전혀
다른 쉬운 추출 문제**다. 두 경로:

1. **패널 캡처 OCR (로컬, 브라우저)** — Tesseract.js 등. 캡처 여러 장 일괄 업로드 → OCR →
   `전산화번호·mx/my·선로번호` 자동 추출 → 표 검토 → 임포트. 타이핑 0, 유출 0.
   - 임포트 핵심값이 OCR 강점 영역: 전산화번호(ASCII), 좌표(숫자, **URL 정규식 추출 + 범위 검증**),
     선로번호(숫자). 한글(선로명·지번)만 보통 난이도 → 검토 보정.
   - **교차 검증**: 좌표가 모바일NGIS(mx/my) + 카카오내비(nx/ny) 두 번 나옴 → 일치 확인으로 오독 차단.
2. **SMS 본문 텍스트** — 가능하면 OCR 없이 정확 파싱. (owner 미확정 → 1번 OCR 경로로 설계)

**owner 확인 (2026-06-13)**:
- **패널 레이아웃이 항상 같은 형식** → 라벨·위치 고정 → **파싱 신뢰도 높음** (라벨 기준 추출 + 좌표
  URL 정규식 + mx/my↔nx/ny 교차검증).
- **전주 전산화번호·위치 데이터는 정보유출과 별개** (망 토폴로지 도면과 다른, 위치 참조 데이터) →
  이 추출은 **로컬 OCR 기본, 필요 시 클라우드 OCR/AI 비전으로 올려도 무방**. (망 도면 캡처의 로컬
  전용 제약은 여기 적용 안 됨)

→ 캡처는 전주마다 어차피 하나씩 뜨므로 그대로, **타이핑만 제거.** 캡처 일괄 업로드 → 자동 추출 →
  검토 → 임포트. 시설 점·전주 좌표 추출의 현실적 해법.

### 핵심 판단

- **경로(선)는 좌표 CSV(방식 A)가 압도적으로 안정적.** owner가 **꺾임점 좌표를 추출 가능**하다고
  했으므로(이전 답변), 20조 평행선을 이미지에서 분리하는 무리수 대신 **좌표를 그대로 넣는다.**
- **시설(점)은 A 또는 B 둘 다 가능.** 좌표가 있으면 A가 정확, 좌표 추출이 번거로우면 B(OpenCV
  검출)로 빠르게 깔고 보정. **둘은 배타적이지 않다** — 시설은 B로 빠르게, 경로는 A로 정확히 조합 가능.
- **AI 비전(D)** 은 계약 확인 시 "더 좋은 방법"으로 열어둠 (시설 종류·연결 해석에 강함). 코드는 이미
  추가해 둠(미사용·안전).

### 권장 통합안

1. **시설**: 좌표 CSV(A) 기본. 좌표 추출이 번거로우면 **OpenCV 검출(B)로 보조** 후 좌표 보정.
2. **경로·케이블**: **좌표 CSV(A) 단독** — 꺾임점 좌표열 + 경로ID. (이미지 선분리 안 씀)
3. **지도 다조**: 평행 오프셋(확대 시 벌어짐). **도식**: 절체용 분리 펼침(상세는 보류).
4. **AI(D)**: 계약 확인 후 옵션으로.

## 2. 핵심 설계 원칙

1. **단일 진실의 키 = 외부 식별자(LGU+ ID)**. 이름 매칭은 깨지기 쉽다(전주·건물 이름 중복). 시설마다
   LGU+ 고유 ID를 받아 `external_id` 로 저장하고, **모든 매칭·재임포트를 이 키로** 한다.
2. **재임포트 = upsert**. `(project_id, external_id)` 기준으로 있으면 갱신·없으면 추가 → **재실행해도
   중복 없음**. "기존 프로젝트 확장"이 자연스럽게 됨.
3. **지도 ≠ 도식 (좌표 비공유).** 좌표는 **지도에만** 반영(`lat/lng`, 경로·평행 정확). **도식은
   절체작업용 명료 연결도** — 케이블을 펼치고 분리해 회선·코어 흐름이 한눈에 보여야 한다. 도식에
   지리 배치를 강제하면 케이블이 붙어 **절체작업을 못 본다**(owner 지적 2026-06-13). 따라서 도식
   `x_hint/y_hint` 는 **지리 투영하지 않고** 기존 자동 펼침·수동 정렬을 쓴다.
4. **경로는 꺾임점 좌표열**. 시작·끝은 시설 좌표가 자동, 중간 꺾임점만 입력.
5. **같은 경로 다조 = 평행 오프셋**(묶음 아님). 확대 시 LGU+처럼 벌어지게(실거리 단위 권장).
6. **업로드 전 드라이런 미리보기**. "신규 N · 갱신 M · 오류 K · 무시 L" 을 보여주고 확정 → 시행착오 차단.
7. **기존 작동 코드 보존**. 새 컬럼·새 임포터·렌더 추가만. 캔버스 라우팅·다조 우회(도식) 로직은 안 건드림.

## 3. 입력 파일 설계 (CSV 4종, UTF-8 BOM, CRLF)

업로드는 모두 **해당 프로젝트의 가져오기 페이지**에서. 순서 의존: ① 시설 → ② 케이블 → ③ 경로점.

### ① 시설 (facilities) — 기존 확장

```
외부ID* · 종류* · 이름* · 함체규격 · 설치주소 · 위도(my) · 경도(mx) · 부모국사 · 비고
```
- **외부ID**: LGU+ 시설 고유번호 (재임포트·케이블 매칭의 키). **신규 컬럼.**
- 위도/경도 = WGS84 십진수. `my→위도`, `mx→경도`.
- upsert: `(project_id, external_id)` 있으면 좌표·이름 등 갱신, 없으면 신규 + 번호 발급.
- 외부ID 비면 → 이름으로 폴백(이름 고유해야 함). 가능하면 외부ID 채우는 걸 권장.

### ② 케이블 (cables) — 매칭 키를 외부ID로 강화

```
케이블ID* · 선로번호* · 출발시설외부ID* · 도착시설외부ID* · 규격* · 상태 · 설치구분 · 코어수 · 사용선번 · 비고
```
- **선로번호 = 경로ID**: 같은 선로(예: 간석간 #40)를 공유하는 케이블 묶음 키. LGU+ 추출 화면에
  `선로명·선로번호`로 바로 나옴. ③ 경로점과 연결. 여러 조가 같은 선로번호를 가짐.
- 출발/도착은 **시설 외부ID(전산화번호)**로 매칭(이름 매칭보다 안전). 기존 이름 매칭은 폴백 유지.
- 코어수·사용선번: 조별로 다를 수 있으니 케이블 행마다.

### ③ 경로점 (route points) — 신규, 전주(꺾임점) 1개 = 1행

```
선로번호* · 순번* · 전산화번호 · 경도(mx)* · 위도(my)* · 지번
```
- **추출 확인 (2026-06-13)**: LGU+ 전주 조회 시 `전산화번호 + mx/my(WGS84) + 선로명/선로번호 + 지번`
  이 한 번에 나옴 → **전산화번호 디코딩 불필요, 좌표 직접 사용**.
- `선로번호` 로 묶고 `순번` 으로 정렬 → 그 선로의 전주들이 경로 polyline.
- 전산화번호 = 전주 고유 식별자(전주를 시설로도 둘 경우 `external_id`).
- **구간거리는 좌표로 자동 계산(Haversine)** → 기별명세서 거리 자동.
- 시작·끝점은 케이블의 출발/도착 시설(함체) 좌표가 자동 → 사이의 전주만 순서대로 넣는다.
- 같은 선로번호를 쓰는 모든 조가 이 경로를 공유(중복 입력 불필요).

### ④ 선로 구성 테이블 (케이블·연결·규격·조수) — 신규 발견 데이터원 (owner 2026-06-13)

owner 가 LGU+ 에서 **표 형식 자료**를 보유. 케이블 구성 + 전주 연결(토폴로지)이 모두 담겨 있다.
주요 컬럼:

| 컬럼 | 의미 | 임포트 매핑 |
|---|---|---|
| 선로번호 (간석간33L10) | 선로 | **경로ID** |
| 현전주관리구 + 현전주번호 (8720E·822) | 현재 전주 = **전산화번호 8720E822** | 전주 식별(external_id) |
| 1차전주관리구/번호, 2차전주관리구/번호 | 인접 전주(99999·999 = 종단/없음) | **연결 = 경로 토폴로지** |
| 규격 (12·36·72·144) | 코어 수 | 케이블 규격 |
| 조수 (0.5·1) | 조 수 | 다조 수 |
| 선로id (4009-2023…·100000…) | 케이블 고유 ID | `cable_code` |
| 공사번호·접속함체·사업자·설치일자 | 메타 | notes/필드 |

**전산화번호 = 관리구 + 번호** (예: 8720E + 822 = `8720E822`). 패널(①)의 좌표와 **이 키로 JOIN**.

**경로 재구성**: `현전주 → 1차전주 → 2차전주` 연결을 따라가면 선로의 전주 사슬 = 경로. 따라서 **③
경로점 CSV 가 불필요할 수 있음** — 이 표(연결) + 전주 좌표(①)만 합치면 경로가 자동 구성된다.

**미확정 (owner 확인 필요)**:
- 이 표가 **엑셀/CSV 로 내보내기 되나**, 아니면 **캡처만** 되나? (export 면 OCR 불필요 — 바로 임포트)
- 전주 좌표는 **패널 1건씩 조회만** 가능한가, **여러 전주 좌표를 한 번에** 받을 길이 있나?
  (표의 전주 수만큼 좌표 조회가 필요하므로, 벌크 좌표원이 있으면 결정적)

### (옵션) 회선 (circuits) — 기존 그대로

`회선번호·설치장소명·종류·상태·비고` (변경 없음).

## 4. 좌표 체계

- **저장**: `lat`/`lng` (WGS84). **지도 모드만** 이걸 카카오 투영으로 그림 (이미 동작).
- **도식은 지리 투영 안 함** (§2-3). 도식 위치(`x_hint/y_hint`)는 기존 자동 펼침·수동 정렬 사용 →
  절체작업 가독성 우선. 좌표 임포트는 도식 좌표를 건드리지 않는다.
- 경로점도 지도용 `lat/lng`(=`mapWaypoints`)만 필수. 도식 경로는 절체용 표현(아래 §6-도식 참조).

### 좌표 확보 전략 (owner 확인: 좌표는 패널 1건씩만 조회됨)

좌표가 전주 1건씩만 나오므로(수백 전주 = 수백 조회) 이게 최대 병목. **표(④)에는 전 전주의 전산화번호가
이미 있으므로**, 전산화번호 디코딩이 "조회 없이 전체 좌표"의 지름길로 다시 유효해진다(앞서 직접좌표
우선으로 보류했으나, 좌표가 벌크로 안 나오는 게 확인됨).

| 전략 | 수고 | 정확도 | 비고 |
|---|---|---|---|
| **A. 전수 조회** | 전주 수만큼 | 정확 | OCR로 타이핑만 제거, 조회·캡처는 남음 |
| **B. 보정 디코딩** | 10~20 조회 | ~25m | 정확 좌표 샘플로 전산화번호→좌표 격자를 fit → 표의 전 전산화번호에 적용. **검증 필요(R&D)** |
| **C. 하이브리드** ⭐ | 함체+주요전주만 조회 | 함체 정확·전주 근사 | 접속점(함체)은 정확, 사이 전주는 디코딩/근사 |
| **D. 지도 캡처 OCR+마커** ⭐ | 캡처당 기준점 2~3 | 좋음(지오레퍼런싱) | **owner 2026-06-13: 줌인 지도 캡처 가능.** 깔끔한 줌에서 전산화번호 라벨 OCR + 마커(흰=전주·빨강=함체) 위치 검출 → 캡처당 다수 전주 좌표. 픽셀→실좌표는 기준점 2~3개로 지오레퍼런싱(또는 디코딩). **전주 1건씩 조회 → 캡처당 기준점 몇 개로 급감** |

**데이터원 3종 종합** (전산화번호로 JOIN):
- **지도 캡처(D)** → 전산화번호 + 위치(벌크) — 좌표 병목 해소
- **선로 구성 표(④)** → 케이블·규격·조수 + 연결(토폴로지) — 연결 최정확
- **전주 패널(①)** → 정확 좌표 (지오레퍼런싱 기준점·검증용 소수)
- 지도 심볼 (owner 2026-06-13):
  - **흰 마커 = 일반 전주**, **빨강 마커 = 변압기 설치 전주** — 둘 다 종류 `일반설치장소`(전주),
    **변압기 여부만 속성/플래그**(예: `has_transformer`).
  - **함체 = 별도 심볼**로 따로 표시 → 마커 검출로 함체 위치도 확보(종류 `접속함체` 계열).
  - **선로 구성 표의 「접속함체」 = 함체 식별/위치** → 지도의 함체 심볼과 표의 연결이 이어짐.
  - 줌이 깔끔해 OCR·심볼검출이 빽빽한 대각선 지도와 달리 현실적.
- **데이터 그림 완성**: 지도 캡처 = 전주(일반/변압기)·함체 위치 + 전산화번호 / 표 = 연결·규격·조수
  ·접속함체 / 패널 = 정확좌표(기준점). 전산화번호로 JOIN → 시설·케이블·경로 전부 구성.

- **권장**: 함체(접속점) 정확이 중요하고 전주는 ~25m 허용이면 **C**. 빠른 전체 배치는 **B**.
- **보정 디코딩(B) 가능성**: 전산화번호 = 관리구(8720E, 지역 격자) + 번호(50m 격자+순번). 한 관리구
  안에서 번호→위치가 격자 선형이면 샘플로 fit 가능. ~25m 양자화가 정확도 하한. **owner 정확도 허용치가
  전략을 결정.**

## 5. 프로젝트 구분 & 기존 프로젝트 확장

- **구분**: 모든 데이터는 `project_id` 스코프. 업로드는 항상 "그 프로젝트의 가져오기 페이지" 안에서
  일어나므로, 파일에 프로젝트 식별자를 넣을 필요 없음(현재 page 가 `project_id` 주입).
- **기존 확장 시나리오**:
  1. 같은 프로젝트에 시설을 추가/수정 → ① 시설 CSV 재업로드. `external_id` upsert 로 **기존은
     갱신, 새 것만 추가**. (중복 없음)
  2. 다른 프로젝트의 시설을 가져와 확장? → **권장하지 않음**. 프로젝트는 공사 단위로 격리. 정말
     필요하면 "프로젝트 복제" 기능을 별도로(범위 밖, 후속).
- **요약**: "기존 시설 확장"은 **같은 프로젝트 안에서 external_id upsert** 로 해결. 크로스 프로젝트
  병합은 이번 범위에서 제외.

## 6. 같은 경로 다조 — 지도 평행 오프셋 (신규, 최난도)

- 같은 `경로ID` 케이블들을 **경로에 수직으로 i번째마다 오프셋** → 평행선.
- **오프셋 단위 = 실거리(미터)** 권장 → 확대 시 간격이 벌어져 LGU+ 화면과 동일. (픽셀 고정은 확대해도
  안 벌어짐)
- 색=규격, 점선=설치구분, 굵기·투명도=상태 (기존 `edgeStyle` 재사용).
- 20조도 확대하면 구분됨. 저배율은 뭉치지만 owner가 확대해서 보므로 OK.
- 도식 모드는 기존 평행분산이 일부 동작 — 경로ID 기반 평행으로 일원화할지는 ③ 단계에서 검토.

## 7. 업로드 UX — 드라이런 미리보기 (시행착오 차단의 핵심)

각 임포트는 **2단계**:
1. **미리보기(dry-run)**: 파일 파싱 + 검증만. 결과 표시:
   - 신규 N · 갱신 M · 오류 K(행번호+사유) · 무시 L
   - 좌표 없는 시설, 외부ID 누락, 매칭 실패 케이블 등 미리 경고
2. **확정**: 미리보기 통과분만 DB 반영.

→ "올렸더니 중복 200개" 같은 사고를 원천 차단. 현재 임포터는 즉시 반영이라, 미리보기 단계를 추가.

## 8. 검증 규칙 (행 단위, 오류 행만 건너뜀)

- 외부ID 중복(같은 파일 안) → 오류
- 종류 enum 불일치 → 오류
- 좌표 형식/범위(위도 33~39, 경도 124~132 권장 범위 밖) → 경고(등록은 허용)
- 케이블: 출발/도착 외부ID 미존재 → 오류 / 같음 → 오류 / 규격 enum 불일치 → 오류
- 경로점: 경로ID 미존재(케이블에 없음) → 오류 / 순번 중복 → 오류
- 인코딩: UTF-8 (BOM 허용). 콤마/세미콜론 자동 감지(기존 csv-parse 재사용).

## 11. 단계별 구현 로드맵 (각 단계 빌드·확인 후 다음)

- **0단계 (지금)**: 본 문서 + 열린 질문 확정.
- **1단계 — 시설 외부ID + upsert** (도식 투영 없음)
  - 마이그: `external_id`. 시설 임포터를 `(project, external_id)` upsert 로 개조.
  - 산출물: 시설 CSV 올리면 **지도**에 좌표대로 배치, 재임포트 중복 없음. 도식은 기존 자동 펼침.
- **2단계 — 케이블 외부ID 매칭 + 경로점 임포트**
  - 케이블 임포터 외부ID 매칭 + 경로ID. 경로점 CSV 임포터 신규(waypoints 채움, 거리 자동).
  - 산출물: 도로 따라가는 경로가 지도·도식에 그려짐.
- **3단계 — 지도 다조 평행 오프셋 (최난도)**
  - 경로ID 공유 케이블을 실거리 수직 오프셋 → 확대 시 벌어짐. 색·점선 유지.
  - 산출물: 4~20조가 LGU+처럼 평행하게 보임.
- **4단계 — 드라이런 미리보기 UX**
  - 각 임포터에 미리보기 모드 + 확정. (1~3 단계에 점진 적용 가능)
- **(후속·보류) 절체용 도식 상세 설계**: 기존 시설 이설 후 **실제 작업환경에서 검토해 확정**
  (owner 2026-06-13). 케이블 분리 펼침·회선/코어 라벨·직선도·전후 비교 중 무엇을 강화할지는 그때.
- **(후속) 분기·정산 검증**: 분기점 함체 모델, 기별명세서 거리 검증 등.
- **(옵션) OpenCV 시설 검출 고도화**: 기본 PoC([ScreenCaptureImport](../src/app/relocation/[id]/ScreenCaptureImport.tsx))
  를 실데이터로 튜닝. 좌표 추출이 번거로울 때 시설 빠른 배치용. 경로(선)에는 미적용(20조 분리 비현실).

| D | 경로 저장 방식 | **`cables.route_id` 컬럼 + 임포트 시 경로 geometry 를 각 케이블 `waypoints` 에 복사.** 캔버스(작동 코드)를 안 건드림 — 지금도 케이블별 waypoints 를 그림. route_id 는 평행 오프셋 그룹·재임포트 동기화용. (별도 routes 테이블은 중복이 부담될 때 후속 리팩터) |
| E | 코어수·사용선번 | 케이블 CSV에 **선택 컬럼**(`코어수`·`사용선번`)으로. 비우면 나중에 캔버스에서 입력 |
| G | 분기(골목 빠짐) | **분기점에 함체/맨홀 시설 + 갈래 케이블**(별도 경로ID). 별도 기능 불필요 |

→ A·B·C·F 확정으로 **1~2단계 포맷·마이그레이션이 잠겼다.** D·E·G 는 권장안으로 진행 가능.

### ✅ 추출 화면 확인 (owner 2026-06-13)

LGU+ 전주 조회 → SMS 내용으로 다음이 **한 번에** 나옴:
- `전산화번호` (예: 8720E312) → 전주 `external_id`
- `mx=126.708941 & my=37.466821` (WGS84 경도/위도) → **좌표 직접 제공, 전산화번호 디코딩 불필요**
- `선로명`(간석간) · `선로번호`(40) → **경로 묶음 키 = 선로번호**
- 카카오내비 링크의 `nt=간석동_111-10` → 지번(주소) 보너스

**전산화번호 좌표 디코딩(반경 25m·공식 비공개)은 폐기** — 직접 좌표가 정확. 전산화번호는 식별자로만.

### 지중 경로 차이 처리 (C 관련)

같은 도로라도 **지중 케이블은 경로(관로 경로)가 가공/구내와 약간 다를 수 있음** → 지중 케이블에는
**다른 경로ID**를 주면 자기 경로점으로 그려진다. 평행 오프셋은 "같은 경로ID 끼리만" 묶이므로,
지중은 가공 다발과 별개 선으로 자연히 분리된다. 추가 로직 불필요 — 경로ID 분리로 해결.
